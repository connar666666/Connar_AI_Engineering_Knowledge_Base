# Rubric、Harness 与 Agent 评测

> 状态：历史重建版。根据过去关于代码类 Rubric 和 Agent 评测的多轮讨论重建。

## 1. Rubric 是什么

Rubric 是一套明确的评价标准，用来回答：

```text
一个任务完成得好，具体应该长什么样？
```

它不是简单的“对或错”，而是把质量拆成可观察、可判定的维度。

例如一个代码 Agent 完成需求后，可以从以下方面判断：

- 功能是否正确。
- 是否满足用户全部约束。
- 是否破坏已有功能。
- 测试是否覆盖关键路径。
- 错误处理是否合理。
- 代码结构是否可维护。
- 是否产生安全或权限风险。

## 2. 为什么 Agent 更需要 Rubric

传统算法题往往有明确输入输出；真实 Agent 任务通常开放、长链路且存在多个合理答案。

没有 Rubric 时，评测容易退化为：

- 只看最终文本是否像正确答案。
- 只看 Agent 是否说“完成了”。
- 不检查真实文件、数据库或浏览器状态。
- 不区分部分完成与真正闭环。

Rubric 将模糊的“看起来不错”转换为可验证标准。

## 3. Harness 是什么

Harness 是执行评测的工程系统。它负责：

```text
准备任务环境
→ 启动 Agent
→ 提供工具和约束
→ 记录完整轨迹
→ 检查最终状态
→ 按 Rubric 评分
→ 输出失败原因和证据
```

因此：

```text
Rubric = 判定规则
Harness = 运行任务并收集证据的评测基础设施
```

## 4. 代码类 Agent Harness

一个代码 Agent Harness 可能包含：

- 固定仓库和起始 Commit。
- 隔离的容器或虚拟环境。
- 明确任务描述。
- 可用工具清单。
- 时间、token 和命令限制。
- Unit Test、Integration Test 和隐藏测试。
- Git Diff、文件状态和命令日志。
- 安全检查与禁止操作。

最终不只看 Agent 回复，而要看仓库真实状态。

## 5. Rubric 设计结构

每个维度建议包含：

```text
评价维度
判定标准
通过证据
失败证据
严重程度
是否必须满足
```

示例：

| 维度 | 通过标准 | 证据 |
|---|---|---|
| 功能正确 | 所有必要测试通过 | test output |
| 需求覆盖 | 用户列出的约束均已实现 | code diff + manual checks |
| 无回归 | 旧测试仍通过 | regression suite |
| 可维护性 | 逻辑位于正确层次，无明显重复 | review evidence |
| 安全性 | 不泄露密钥、不绕过权限 | static and runtime checks |

## 6. 评分方式

可使用：

- 二元门槛：必须通过 / 失败。
- 分档评分：0、1、2、3。
- 加权评分：关键功能权重更高。
- 硬约束加软评分：安全失败直接判零，其余按质量评分。

关键要求是同类任务保持一致，避免评测者随意改变标准。

## 7. 结果评分与过程评分

### 结果评分

检查最终产物：

- 代码是否正确。
- 页面是否真实可用。
- 数据是否写入正确位置。
- 测试是否通过。

### 过程评分

检查 Agent 的执行轨迹：

- 是否先阅读相关代码。
- 是否进行了验证。
- 是否忽略错误。
- 是否执行危险命令。
- 是否在没有证据时宣称完成。

结果优先，但过程信息有助于定位失败模式和改进 Agent。

## 8. 常见 Rubric 缺陷

- 标准太抽象，例如“代码质量好”。
- 多个评价维度重叠。
- 无法通过环境自动或人工验证。
- 把实现方案写死，而不是评价目标。
- 忽略边界条件和回归。
- 只评最终文字回复，不评真实系统状态。

## 9. Agent 安全比赛中的 Harness

攻击类 Agent 评测还需要记录：

- 攻击 Prompt。
- 多步工具轨迹。
- 是否真正触发禁止行为。
- 是否只是模型口头答应，但没有执行。
- Replay 后是否仍稳定成功。
- 成功是否依赖随机性或环境泄漏。

一次偶然命中不能直接视为稳定攻击，应重复验证并保存证据。

## 10. 最终理解

Rubric 和 Harness 的价值是让 Agent 能力从“演示看起来不错”走向可重复、可比较、可定位失败的工程评测。

```text
任务定义
+ Rubric
+ 隔离环境
+ Harness
+ 可验证证据
= 可信 Agent Evaluation
```
