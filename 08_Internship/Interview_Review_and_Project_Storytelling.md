# 实习面试：复盘方法与项目讲解

## 1. 复盘文档的标准结构

每个问题都按下面格式整理：

```text
面试官问题
我的原回答
回答中的有效部分
没有回答好或答错的部分
更好的回答
可以引用的项目证据
需要补学的知识
```

不要只把逐字稿重新排版，否则下一次面试仍然不知道如何改进。

## 2. 回答项目问题的四层结构

### 第一层：业务问题

先说为什么需要这个项目，而不是先报技术栈。

Transfer Agent 的业务目标可以概括为：

```text
用户不需要手工理解复杂时间线结构，
而是通过自然语言把已有内容迁移、替换或重组为新的可编辑结果。
```

### 第二层：系统架构

```text
用户输入
  ↓
Web 前端收集当前项目状态
  ↓
后端鉴权、加载版本并构造 Agent Context
  ↓
Transfer Agent 生成结构化操作
  ↓
后端校验并应用操作
  ↓
前端显示 diff 和 Remotion 预览
```

### 第三层：个人工作

需要明确说自己具体负责：

- 哪个模块。
- 解决了什么问题。
- 改了哪些数据流或接口。
- 如何验证。
- 与其他成员如何协作。

避免只说“我们做了”。

### 第四层：结果与反思

包括：

- 性能或体验提升。
- 当前限制。
- 发现的架构问题。
- 下一步优化方案。

## 3. 如何回答“怎么保证最终迁移效果”

迁移效果不能只依赖一次 LLM 生成，而应由多层机制保证。

### 3.1 输入质量

- 提供规范化的当前状态。
- 只加入与任务相关的素材和时间线片段。
- 保留用户已经确认的约束。
- 避免把过期 Snapshot 混入当前状态。

### 3.2 输出约束

- 要求 Agent 输出结构化 operations。
- 使用 schema 校验字段。
- 所有目标元素必须引用真实 ID。
- 限制允许的操作类型。

### 3.3 后端验证

- 验证项目版本。
- 验证元素和资产存在。
- 验证权限。
- 验证时间线范围、时长和冲突。
- 失败时不落库，并返回可重试错误。

### 3.4 前端验证

- 展示修改 diff。
- 提供预览。
- 对高风险操作要求用户确认。
- 支持撤销或恢复版本。

### 3.5 评测

可设计：

- 操作成功率。
- 目标元素命中率。
- 时间线合法率。
- 用户二次修改率。
- 多轮任务完成率。
- 单次迁移 token 和延迟。

面试回答应强调：

```text
模型负责生成候选修改，系统通过 schema、后端规则、版本控制、预览和评测保证结果可用。
```

## 4. 如何回答上下文膨胀问题

### 现象

每轮 Agent View 如果累积此前所有时间线 JSON，会导致：

- token 不断增长。
- 多个历史版本同时进入上下文。
- 模型引用旧状态。
- KV Cache 命中并不能抵消无效计算和幻觉。

### 根因

把持久化历史和 LLM 工作上下文当成同一个东西。

### 方案

```text
Event Log + 周期 Snapshot 用于恢复
当前状态 + 最近窗口 + 有效约束摘要用于 LLM
需要过去信息时按需检索
```

### 面试中的进一步说明

不要只说“使用滑动窗口”。完整回答应说明：

- 哪些内容保留。
- 哪些内容压缩。
- 哪些内容按需检索。
- 如何确保长期约束不丢失。
- 如何评估优化是否有效。

## 5. 如何回答 KV Cache

KV Cache 缓存的是模型计算产生的键值张量，适合同一稳定前缀重复使用。

系统可以稳定：

- System Prompt。
- Tool Schema。
- 输出协议。
- 领域规则。

但不应为了缓存而保留：

- 过期时间线。
- 全部历史 Snapshot。
- 每轮重复的巨型 JSON。

好的设计是稳定前缀与动态后缀分离。

## 6. 如何回答 Agent 幻觉

Agent 幻觉不只靠 Prompt 解决。工程防线包括：

1. 结构化输出。
2. ID 和版本校验。
3. Tool 参数白名单。
4. 后端事务。
5. 检索真实数据。
6. 高风险操作确认。
7. 失败重试时保留明确错误。
8. 评测和日志。

回答时应把“模型能力问题”转化为“系统如何限制错误影响”。

## 7. 常见回答问题

### 只讲技术名词

错误示例：

```text
用了 React、FastAPI、Redis、LLM、Docker。
```

问题是没有说明为什么使用、数据如何流动和自己做了什么。

### 把设计目标说成已经实现

应该区分：

- 已经落地。
- 正在重构。
- 讨论中的方案。
- 未来优化。

### 没有量化结果

如果暂时没有线上数据，可以诚实说明，并提供已经可测量的指标和测试结果，不能凭空编造提升百分比。

### 回答没有闭环

每个项目答案至少形成：

```text
问题 → 方案 → 实现 → 验证 → 限制
```

## 8. 项目介绍模板

```text
这个项目解决的是……
用户原来需要……，现在可以……
整体架构分为前端、后端、Transfer Agent 和渲染模块。
我主要负责……
最关键的技术难点是……
我们通过……保证结果正确。
当前发现的主要问题是……
下一步会通过……优化，并用……指标验证。
```

## 9. 后续补强清单

- 为项目画一张标准架构图。
- 准备一条完整请求的数据流。
- 准备一个真实失败案例和修复过程。
- 记录实际接口、文件路径和测试。
- 补充 token、延迟、成功率等基准数据。
- 将原始面试逐字稿逐题映射到本文结构。
