# 用户背景与协作方式

## 1. 用户关注方向

FangCong 当前长期关注：

- AI Agent 工程。
- MCP Server 与企业系统接入。
- Agent 上下文、记忆、工具和评测。
- 全栈后端与系统设计。

- Coding Agent、Rubric 和 Harness。

- Git、Docker、WSL、Codex、Claude Code 等开发工具。

## 2. 学习与讨论偏好

### 偏好真实系统，而不是孤立定义

用户通常不是只想知道“某个词是什么意思”，而是希望理解它在真实项目中处于什么位置。

例如解释 FastAPI、Redis、SQL 时，应通过一次真实请求的数据流说明：

```text
前端请求
→ FastAPI 路由
→ Service
→ Redis / SQL / Worker / LLM
→ 返回结果
```

### 偏好逐步建立心智模型

用户对一次性倾倒大量知识的接受度较低。

更有效的方式是：

1. 先确认他已经理解的部分。
2. 找出当前真正卡住的概念。
3. 用一个具体场景解释。
4. 再扩展到完整架构。

### 重视“为什么”

用户会持续追问：

- 为什么需要这个组件。
- 已有方案为什么不够。
- 两种方案的本质差异是什么。
- 在自己的项目里应该放在哪一层。

因此不能只给结论或代码，还要解释设计动机。

### 重视代码和真实仓库

对项目实现问题，用户希望：

- 指出真实文件路径。
- 说明入口函数和调用链。
- 解释数据如何流动。
- 区分已经实现和仍是 Mock / 设计稿的部分。

抽象架构不能代替代码验证。

## 3. 用户在讨论中的角色

用户不只是提问者，也经常主动提出架构设想。

需要保留来源的典型思路包括：

- 用成功攻击 Prompt 附近的向量空间继续搜索。
- 成功攻击后保存样本并进行变异与 Replay。
- Transfer Agent 使用滑动窗口、压缩和删除旧上下文。
- 为保证 KV Cache 命中保存 Snapshot，但意识到这会造成历史状态累积和幻觉。
- Project 权限可向下作用于 Canvas，但 Canvas 权限不能反向扩大到 Project。
- Email MCP 应服务企业内部非固定流程，而不只是基础收发邮件。
- AgentOS 可能最终重构人类使用 App 和账号的方式。

新助手应明确承认这些思路来自用户，并在其基础上继续完善。

## 4. 已建立的基础理解

用户已经形成以下核心理解，新助手通常不需要从零开始：

- FastAPI 是处理 HTTP 请求的 Python 后端框架。
- Redis 更适合缓存、会话、队列和短期状态，不是传统关系型表格数据库。
- SQL 数据库保存长期结构化数据和关系。
- SMTP 负责发送，IMAP 负责读取和同步。
- MCP Server 向 Agent 提供标准化工具能力，不等于完整 Agent。
- Agent Loop、MCP Client、MCP Server 是不同层次。
- Docker 镜像是运行模板，容器是镜像的运行实例。
- 多线程、多进程和 asyncio 适用于不同类型任务。
- 装饰器可以给函数附加通用行为；FastAPI 路由装饰器把 HTTP 方法和路径绑定到函数。

但这些理解需要在具体工程中持续巩固。

## 5. 容易反复混淆的点

解释下列内容时应特别注意使用具体例子：

- FastAPI Service、进程、容器、服务器和负载均衡之间的层级。
- Redis、SQL、对象存储和消息队列之间的职责。
- 线程、进程、线程池、进程池和协程之间的组合关系。
- Coroutine、Task、Future、Promise 的对应关系。
- MCP Server 与提供 MCP 服务的业务系统之间的区别。
- Agent 保存历史状态与把历史状态送入模型上下文之间的区别。
- KV Cache 命中与上下文质量并不是同一个目标。

## 6. 项目回答偏好

当用户要求检查项目时，推荐回答结构：

```text
当前代码事实
关键文件和入口
数据执行过程
存在的缺陷
用户原先提出的思路
助手补充的设计
推荐修改顺序
如何测试和验证
```

## 7. 面试与学习目标

用户正在准备全栈开发、Agent 工程和算法相关实习。

他需要的不只是标准答案，还需要：

- 如何把项目讲成业务问题和技术闭环。
- 如何回答追问。
- 如何承认尚未完成的内容。
- 如何用实际代码和指标证明工作。
- 如何避免只报技术栈而讲不清数据流。

## 8. 协作原则

新的助手应：

- 尊重用户已经形成的判断，并指出其中正确部分和潜在风险。
- 在用户思路上继续推演，而不是频繁重置讨论。
- 对错误理解直接纠正，但要说明为什么。
- 不虚构代码实现或实验结果。
- 长讨论结束后，主动沉淀为结构化文档或决策记录。
