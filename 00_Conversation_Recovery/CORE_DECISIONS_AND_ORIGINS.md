# 核心决策与思路来源

本文件只记录跨多轮讨论后形成的高价值决策，以及它们最初由谁提出。

## 1. Transfer Agent 上下文不能等同于历史存储

- **用户提出**：历史 Agent View JSON 持续累积，导致上下文变长、KV Cache 与幻觉问题。
- **用户提出**：考虑滑动窗口、压缩和删除旧内容。
- **助手补充**：将 Event Log、Snapshot、Current State 和 LLM Working Context 分层。
- **共同结论**：完整历史保存在数据层；模型只接收唯一当前状态、近期操作、有效约束摘要和按需检索历史。
- **当前状态**：设计结论，待真实代码验证和性能评测。

## 2. Transfer Agent 应输出结构化操作，而不是完整状态副本

- **助手补充**：Agent 输出 `operations`、`base_version` 和解释，后端校验并应用。
- **用户认可的目标**：减少重复 JSON、避免旧状态覆盖、提高可撤销和可审计性。
- **共同结论**：状态是系统事实，Agent 只生成候选操作。
- **当前状态**：架构方向，待代码落地。

## 3. KV Cache 命中不是保留无限历史的理由

- **用户提出**：过去保存 Snapshot 的动机之一是保证 KV Cache 命中。
- **用户进一步指出**：这种做法反而造成上下文膨胀和多个历史状态冲突。
- **助手补充**：稳定 System Prompt、Tool Schema 和领域规则适合作为缓存前缀；变化状态应放在动态后缀。
- **共同结论**：缓存效率和上下文正确性必须分开优化，优先保证当前状态单一且可靠。

## 4. Email MCP 的职责边界

- **用户提出**：项目服务集团内部 OA Agent，重点是邮件查询、收发、历史追踪、会话聚合和非固定业务流程。
- **用户提出**：希望复用 OA / 企业微信 SSO，减少用户单独配置。
- **助手补充**：SSO 身份、邮箱账号、邮箱凭据是三层不同概念。
- **共同结论**：OA Agent 管身份、策略、用户确认和审计；Email MCP 管协议和工具；邮箱服务器管数据、账号和服务端限制。

## 5. Email 线程不能只靠主题

- **用户关心**：IMAP 是否能直接按 thread 获取整个会话。
- **助手补充**：不能假设所有服务器有原生 thread id，应优先利用标准邮件头建图。
- **共同结论**：协议线程使用 `Message-ID`、`In-Reply-To`、`References`；语义上的业务线程属于额外推断层，必须和服务器事实区分。

## 6. Tool 与 Skill 必须分层

- **用户发现**：当前 Email MCP 中的 Skills 过于简陋，需要检查 Tool List 和 Prompt 组织。
- **助手补充**：Tool 是可独立执行和测试的原子能力；Skill 是多工具编排说明，不能承担权限和参数校验。
- **共同结论**：安全边界必须放在工具和服务端，Skill 只负责任务规划与调用顺序。

## 7. Project 权限向下继承，但 Canvas 权限不反向扩张

- **用户提出并纠正早期设计**：Project 下有多个 Canvas；Project 权限可复用给 Canvas，但只被邀请到某个 Canvas 的用户不应自动获得整个 Project 权限。
- **助手补充**：Project Member、Canvas Member、Project Invitation 和 Canvas Invitation 应独立建模。
- **共同结论**：权限继承是非对称的，邀请记录必须保留状态和审计。

## 8. Agent Attack 应从随机试探升级为反馈驱动搜索

- **用户提出**：成功 Prompt 应保存、变异、Replay，并利用 hit 结果继续搜索。
- **用户提出**：在 embedding 空间中搜索成功 Prompt 周边，减少重复规则和无方向变异。
- **助手补充**：分离 Search、Mutation、Replay、Verification、Dedup 和 Harness；失败样本也应保存。
- **共同结论**：Harness 和成功判定是系统核心，搜索策略要可复现并利用历史反馈。

## 9. AAAI 论文修改必须从真实实验入口反推

- **用户提出**：先读 `run_lbf_rule_discover_shaping.sh`，理解整个实验顺序，再修改论文。
- **助手补充**：建立代码模块、实验产物和论文段落的映射表。
- **共同结论**：未核对代码前不能假设奖励公式、规则表示或实验组合；论文结论必须有代码和结果证据。

## 10. 学习应使用真实场景逐步展开

- **用户反馈**：一次给出大量线程、进程、asyncio 等零散知识，学习效率很低。
- **助手调整**：用一个真实服务同时解释 asyncio、线程池和进程池的组合。
- **共同结论**：后续技术学习先从项目场景和数据流切入，再解释概念与代码。

## 11. 面试项目回答必须形成闭环

- **用户目标**：不仅知道技术，还要能回答面试官关于项目效果、架构和缺陷的追问。
- **助手补充**：回答结构为“问题—方案—实现—验证—限制”，并明确个人贡献。
- **共同结论**：不能只报 React、FastAPI、Redis 等技术栈；必须讲清请求如何流动、如何保证正确、如何测试。

## 12. AgentOS 的长期判断

- **用户提出**：未来 Agent 可能成为设备管理者，人类不再手动管理 App 和账号。
- **助手补充**：当前 OS Agent 是在既有系统上的过渡形态，AgentOS 是为 Agent 原生设计权限、调度、记忆和能力接口。
- **共同结论**：方向具有现实可能性，但受制于安全、可靠性、生态开放和系统级权限设计。

## 更新原则

只有当下列情况发生时更新本文件：

- 原有决策被代码证伪。
- 用户提出新的核心架构方向。
- 讨论形成新的共同结论。
- 一个设计从设想进入真实实现。

普通技术细节应更新对应项目文档，不在这里重复。
